# GUI 实际操作测试报告

> 日期：2026-07-29
> 环境：`http://127.0.0.1:8013` 与 `:8014`、本机 Google Chrome、Playwright、真实 FastAPI/React、独立 GUI 测试账号
> 说明：内置 Browser 的 `iab` 不可用，依照用户要求改用 Playwright。本报告只记录真实页面点击与真实 HTTP 结果，不把源码检查或 mocked 组件测试写成 GUI 结论。

## 1. 本轮真实操作结论

### 输入、附件与运行状态

- 输入框可以正常发送。发送后发送按钮立即替换为“停止”，停止或终止后恢复发送按钮。
- 一次选择两张眼科图像成功，附件菜单自动关闭；两个预览卡显示在 Composer 上方。
- 消息被接受后，两个附件仍显示在用户消息文字上方，可单独打开。
- 运行从接受输入时开始计时；进行中使用三点脉冲，没有圆圈旋转。
- 公开过程按实际进度追加。影像任务刚开始时页面只有 1 个进行中步骤，没有预先铺开全部 pending 计划。
- 点击停止后 Run 进入终止状态，Composer 立即恢复可输入。

### Skill 与插件

- 点击 Composer 的“技能”按钮打开已验证、已启用 Skill 的多选菜单，没有触发文件上传器。
- 菜单实际列出 `guideline retrieval`、`ophthalmic imaging`、`ophthalmic interview`、`ophthalmic report`、`red flag triage`。
- Skill 导入移至“技能”工作区；导入、验证、启用后才会出现在 Composer 选择器。
- 插件仍通过 `@插件` 选择，按钮显示实际插件名称；公开目录只保留病灶定位、辅助评估、报告生成三项，问答与知识检索作为默认能力。
- 病灶定位与辅助评估可在同一轮同时选择；不选择时由路由器自动组合专业插件。

### 回答版本与操作栏

- 已有“什么是青光眼？”会话含 3 个历史回答版本，上一版/下一版按钮确实切换不同正文。
- 点击重新生成后旧回答立即从当前视图消失，新 Run 显示为“回答 4 / 4”；不是在旧回答下方再追加一份。
- 新 Run 可立即停止，停止后发送按钮恢复；历史回答仍可通过版本按钮切回。
- 点赞按钮可点击，`aria-pressed=true`，刷新后状态持久化。
- 点赞曾暴露一个真实计时缺陷：它会更新 `run.updated_at`，使 34 秒任务显示为 692 分钟。现已改用不可变终止事件计时，复验仍为 34 秒。
- 朗读按钮实际经历“朗读回答 → 取消准备朗读/停止朗读 → 朗读回答”，再次点击会暂停当前音频并取消后续分段。
- 三点菜单为不透明白色，包含单一“导出”、在其下方的“转为文档编辑”以及“删除此回答”。
- 导出子菜单包含 MD、PDF、DOCX、JPG 四种格式。
- 全局操作悬浮说明已覆盖按钮、图标按钮、`summary` 菜单和导出链接；鼠标停留显示中文说明，键盘聚焦也会显示。
- Playwright 实测：“选择本次任务使用的技能”“发送当前消息”“打开账户与模型供应商设置”“打开对话：什么是青光眼？”“重新生成回答”“更多操作”均正确显示。

### 公开过程与引用

- 已完成问答只显示实际发生的“检索可追踪医学证据”“生成回答”两个阶段。
- 展开检索阶段可见：阶段用时 8 秒、筛选出 8 条来源，以及前三条来源标题。
- 普通用户不显示私有 chain-of-thought；只显示公开阶段、关键动作和关键结果。
- 内部 Agent/组件名称已从公开摘要中清理。
- 鼠标悬停正文引用，实际显示来源标题、段落定位和回答采用的对应原文。
- MD 导出不再包含 `[ev_...]` 内部 ID，会转成编号并追加“参考来源”，包含标题、链接、定位和引用文本。

### 三个专业插件真实影像回归

- 通过 GUI 上传 `glaucoma_postoperative_followup.jpg`，同时选择“病灶定位”和“辅助评估”后成功发送。
- 首轮真实任务暴露两个 harness 缺陷：同一附件被 `attachment_ids` 与 `image_paths` 重复计数而误入 Deep；下游文本模型把多模态观察误写成“未提供原始图像”。两项均已由代码修正。
- 重新生成后耗时由 1 分 47 秒降为 58 秒，不再运行无必要的专科复核；页面显示“回答 2 / 2”，旧回答仍可切回。
- 多模态组件没有返回可靠坐标时，页面显示独立的“未形成坐标标注”原图卡和“0 个区域”，明确说明系统未补造病灶边界。
- 辅助评估卡按候选项展示“支持 / 反对 / 仍缺”，只使用“支持有限 / 中等 / 较强”，并明确“支持程度不是患病概率”。
- 后端对上传事实、空坐标披露、无确证分期和直接治疗指令增加代码级校验与措辞收敛；专业插件最终正文先完成结构校验再进入公开输出。
- GUI 还发现发送/停止按钮切换后旧 tooltip 残留；MutationObserver 现会在 React 替换活动按钮时清除旧提示，复验悬停发送按钮显示“发送当前消息”。

### 文档工作区

- 对无产物回答点击“转为文档编辑”，右侧打开可编辑文档工作区。
- 编辑 Markdown 后，右侧预览同步变化；700 ms 防抖后状态变为“已保存”。
- 键盘在宽度分隔线按 `ArrowLeft`，抽屉由 640 px 变为 660 px；宽度写入 `localStorage`。
- 点击关闭前如仍有未保存内容会先保存，失败则保留抽屉并提示。
- 四种产物导出均为 HTTP 200：

| 格式 | Content-Type | 文件签名 |
|---|---|---|
| MD | `text/markdown` | UTF-8 文本 |
| PDF | `application/pdf` | `%PDF` |
| DOCX | Office Open XML | `PK 03 04` |
| JPG | `image/jpeg` | `FF D8 FF E0` |

### 语音

- 用 Playwright 的模拟麦克风验证：点击语音输入后进入“停止录音并转写”，录音可停止；实时语音对话框可打开和退出。
- 模拟麦克风是静音流，因此该次转写按预期返回 ASR 400 并显示可关闭错误，文字输入不受影响。
- 另生成无真人隐私的 WAV 案例 `ophthalmic_plugin_test_cases/audio/glaucoma_followup_question.wav`，通过真实 `/api/v1/audio/transcriptions` 调用：
  - HTTP 200；
  - 转写结果：`OCT检查在青光眼评估中主要看什么。`
- TTS 服务实际返回 HTTP 200，朗读可以再次点击停止。

### 个人供应商设置

- 设置页实际显示 8 张配置卡：Agent、Sub-agent、ASR、TTS、Embedding、Reranker、联网搜索、MinerU。
- 模型类卡片有 URL、模型名、API 密钥；联网搜索有 URL、API 密钥；MinerU URL 固定为 `https://mineru.net/api/v1/agent/parse/file`，只允许配置 Token。
- 页面明确提示模型服务仅支持 OpenAI API 兼容协议，密钥保存后不回显。
- 将联网搜索切为个人配置、填写 URL/密钥并保存后，刷新仍保持个人配置，密钥只显示“已保存”；随后已切回系统默认并再次保存。
- 最终 API 复核 8 项均为 `use_default=true`，没有给测试账号遗留无效供应商配置。

### 受控持续改进

- 真实浏览器进入设置页，`/api/v1/evolution/status` 返回成功；页面显示“受控持续改进”和“生产自动变更：关闭”。
- 当前开发环境已从 `medical_agent_hust/evolution/upstream` 安装官方 A-Evolve 0.1.0 与 GEPA 0.1.1，启动后的 capability 均为 `ready`。
- 项目外 sealed-test 套件已配置并经控制器实际加载：12 例，普通、复杂、高风险各 4 例；manifest 明确禁止候选访问并声明未复用历史评测输出。
- 页面实际展示已观察任务、有效反馈和待离线评测候选数量，并明确区分 Memory、Skill 和晋升边界。
- 真实模型 E2E 点击点赞后，`continuous_state.json` 出现 1 条当前有效反馈；取消或切换反馈使用同一 Run 指纹覆盖，不会重复累计效用。
- 实际检查 `signals.jsonl` 与状态文件，不含本次“什么是青光眼”问题正文、回答正文、`user_id`、附件或证据文本。
- 粗粒度回答负反馈不降低任何 Memory 权重；病史、用药和过敏不参与在线重排。只有重复获得正反馈且达到最小样本的已确认非临床偏好，才允许最高 +15% 的召回增益。
- Skill 只按真实 Agent 实际加载的 Skill 归因；重复负反馈达到门槛后生成去内容化离线候选，不会自动修改或禁用 `SKILL.md`。
- 晋升门禁经测试覆盖：已通过病例变失败、任一切片回归、高风险单病例降分、医疗安全/引用门禁失败、关键错误、样本切片不足、Token 或延迟超限均拒绝。
- 即使 sealed test 全部通过，仍必须由可信控制器生成 HMAC 认证，并由人工审批记录绑定当前 candidate commit；生产运行时没有自动改写入口。
- 1440×900 实际截图中，持续改进卡与供应商配置层级清晰，无横向溢出；移动视口回归通过。

## 2. 视觉结果

主要复验视口为 1440×1000：

- 全局字号为原设计的 1.2 倍，Composer 正文字号实测 16.8 px。
- 单列消息流、底部 Composer 和按需右侧文档工作区关系清晰。
- 字号回调后，设置页仍保持两列供应商卡片并可纵向滚动，没有横向溢出。
- 回答菜单背景实测 `rgb(255, 255, 255)`。
- 上传预览、用户消息附件、运行步骤、引用和回答版本在同一主阅读流中。

此前的响应式与可访问性回归覆盖 980×780、iPhone 13，以及 axe serious/critical violations 为 0。
